# 异常、日志与可靠性

## 异常处理

- 异常不用于正常流程控制，不捕获 NPE 等运行时异常来代替前置校验。
- 禁止空 `catch`。捕获异常后必须恢复、转换为领域异常或重新抛出，并保留原始 cause。
- 捕获范围应与可处理能力匹配。仅在线程入口、任务调度、插件隔离等最外层边界兜底 `Throwable`，不得普遍吞掉 `Error`。
- 禁止在 `finally` 中 `return`。可关闭资源使用 try-with-resources；处理中断异常时恢复中断标记。
- 异常信息提供稳定、可理解的业务语义，不向调用方泄露堆栈、SQL、密钥或内部实现细节。

## 日志

- 不得因无关需求删除、缩减、改写现有日志，或调整现有日志级别和打印逻辑。
- 只有用户需求明确涉及日志，或现有日志导致安全问题、编译失败时，才修改现有日志并说明影响。
- 新增日志沿用项目已有格式；没有格式约定时使用 `[业务][功能][场景]`。
- 进入实际业务后记录关键节点。外部调用只有收到响应后才能记录响应相关字段；失败时记录接口标识、耗时、错误类型和必要定位字段。
- 新增日志必须保留排障需要的现场信息和异常堆栈，但不得新增明文个人敏感信息、密码、密钥、Token 或完整认证信息。
- 不在 DAO、Service、Controller 对同一异常重复打印。由最能表达业务现场且负责处置的边界记录。
- 审计或操作日志优先构造精简的 before/after 摘要，记录操作来源、关键状态和必要数量；不直接序列化完整实体作为新增日志。
- 使用参数化日志；仅当参数计算、序列化或 `toString` 明显昂贵时预先判断日志级别。生产代码不新增 `System.out`、`System.err` 或 `printStackTrace`。

## 外部调用与重试

- RPC、HTTP、MQ、缓存和文件等外部动作不默认放入长数据库事务。
- 远程调用明确连接超时、读取超时和连接池获取超时，并使总调用耗时受上游请求预算约束。
- 只有幂等操作或带可靠幂等键的操作，且异常属于瞬时可恢复故障时才重试。重试必须有次数上限、退避和抖动，禁止无界、递归或固定间隔重试。
- 重试时间计算优先收口为无副作用、可独立测试的策略，并明确最大次数和最大间隔。持久化外部错误时将稳定错误类型与可变错误描述分开，按字段上限截断描述。
- 熔断、限流和降级根据业务可用性、一致性与容量设计，不给普通调用机械增加。降级路径必须确认不会把故障转移并放大到数据库或其他下游。
- 外部依赖失败时不得伪造成功。失败、排队补偿、降级结果和最终一致性状态应在契约中明确。

## MQ、异步与幂等

- 数据落库与消息发布需要一致性时，优先使用项目现有可靠消息能力或事务 Outbox：业务数据与消息记录在同一本地事务提交，提交成功后才尝试立即投递，并保留扫描补偿。普通“发送失败后再写本地表”不能保证原子性，不得描述为可靠 Outbox。
- 消息状态必须区分“已发送”和“业务已完成”。内部消费仍决定最终结果时，发送成功不得直接标记完成；发送、消费、重试、超时恢复和死信状态使用带期望旧状态的条件更新，防止并发覆盖。
- MQ 消费、重试、定时任务、支付和资源创建必须明确幂等键、数据库唯一约束、状态迁移和重复请求结果。
- 异步化只用于允许延迟、失败或最终一致性的流程。后续步骤依赖结果、需要立即反馈或要求强一致时不得盲目异步。
- 异步任务明确线程池、拒绝策略、Trace/MDC/租户上下文传递、异常去向、任务丢失策略、重复执行和优雅停机行为。
- 关键流程按项目现有观测能力记录耗时、成功率、错误码、重试次数、队列积压等指标；普通小改动不为形式新增整套观测系统。

## 缓存

- 明确缓存是性能层还是权威数据源，说明数据来源、更新与失效顺序、一致性窗口和失败行为。
- 根据场景处理穿透、击穿和雪崩；不得默认套用布隆过滤器、分布式锁或多级缓存。
- Redis 不可用时，根据数据库容量和一致性要求选择限流、快速失败、短期本地缓存或受控查库，禁止无条件把全部流量降级到数据库。
- 分布式锁使用项目已有可靠实现，必须校验锁所有权并安全释放；禁止用固定字符串值加无条件删除实现锁。
