# 编码与设计

## 流程编排

- 入口方法按业务顺序体现“校验、准备、核心处理、返回”等真实阶段，读者从上到下能理解主线。
- public 方法负责业务编排；protected/private 方法承载可复用逻辑或边界完整、稳定的能力。字段、构造/注入、public、protected、private 依次排列，私有方法按主流程调用顺序放置，重载方法相邻。
- 当入口或关键 public 方法包含至少三个实质业务阶段，且方法调用本身不足以表达流程时，可以添加简短编号注释。简单方法不为形式添加步骤注释。
- 抽取方法应减少真实复杂度。单次字段赋值、简单判断或循环、参数转发及一次性读写通常内联；跨处重复达到三次时再考虑公共 helper，边界清晰的稳定业务能力可以提前抽取。
- Controller、认证、事务、审计、Feign 等边界允许轻量委托；禁止无职责跳板层。

## 可读性与注释

- 使用项目已有英文词汇，同一业务概念统一动词。方法名优先使用 `validateXxx`、`buildXxx`、`convertXxx`、`saveXxx`、`syncXxx` 等准确动词，避免 `processData`、`doXxx`、`getResult` 等含糊名称。
- 类使用 UpperCamelCase，方法和变量使用 lowerCamelCase，常量使用 UPPER_SNAKE_CASE，包名使用小写；项目已有命名和外部协议字段优先。
- 禁止难懂缩写、无语义占位名及中英文混杂；业务专有名词、品牌名和外部契约命名可以沿用。
- 命名先说明代码做什么。注释用简短内容说明关键业务规则、原因、边界或必要妥协，使读者快速理解即可；避免长篇解释、复述代码或为了形式添加注释。
- 幂等、锁、状态机、吞异常和临时妥协必须简短说明原因。
- JavaDoc 用于公共 API、抽象契约、扩展点及不易从签名理解的行为；简单实现不重复代码。有参数、返回值、异常或空值契约时写清关键含义。
- 不强制 `@Author`、`@Date`。当前项目已使用 Swagger/OpenAPI 时，Controller、接口方法和模型字段沿用现有注解体系；项目未使用时不主动引入。
- 优先遵循 formatter 和 Checkstyle；项目没有格式规则时以可读性为准，160 字符作为软上限。复杂条件、泛型、链式调用和多个副作用可按语义换行。

## 简化与结构

- 不为“以后可能”增加扩展点。只有真实变化点、独立职责或明确契约才增加模式、层或 DTO。Action/Interceptor 仅用于多个真实动作共享稳定的前置、核心、后置和异常生命周期；前置按顺序执行，后置与异常回调按逆序执行，并明确后置步骤失败是否影响主结果。
- 一个类围绕同一职责或内聚用例集合组织。出现无关变化原因时再拆类，不以行数或操作的数据对象数量机械拆分。
- 同一业务规则尽量收口；DTO、Converter、Mapper 等边界同步变化属于正常传播，但转换逻辑应集中并检查调用方。
- 禁止新增循环依赖。维护存量系统时，不为无关需求强制重构既有循环依赖；本次改动不得通过延迟注入掩盖新问题。
- Service/DAO 是否采用 Interface + Impl，遵循项目现有结构；只有多实现、替换边界、模块契约或代理需求时新增接口。
- Lambda、Stream、Optional 能减少样板且一眼可懂时使用；存在多层嵌套、复杂副作用或调试困难时改用普通 if/for。
- 方法建议不超过 80 行、类建议不超过 1000 行。超出时先判断是否存在自然职责边界，不为压行数制造碎片方法。

## Java 正确性

- 覆写方法使用 `@Override`；覆写 `equals` 时同步覆写 `hashCode`。
- 包装类型使用 `Objects.equals` 或明确的 `equals` 比较，避免引用比较和自动拆箱 NPE。
- 金额和精确小数不得使用 `float`/`double`。按项目契约使用最小货币单位整数或 `BigDecimal`；`BigDecimal` 使用字符串或 `valueOf` 构造，数值比较使用 `compareTo`。
- 优先使用 `java.time`，正确区分 `yyyy`、`MM`、`mm`、`HH`、`hh`，不得写死一年 365 天。
- 使用集合时检查可变性、空值、重复 key、`subList` 视图和并发修改语义。增强 for 中不直接增删当前集合；`Collectors.toMap` 明确重复 key 策略。批量输入按业务语义去空、去重或分组；响应顺序与输入相关时显式使用有序集合。
- 业务状态、类型、结果和跨处固定值先复用已有常量或枚举；避免散落的业务魔法值。`long` 字面量使用大写 `L`。
- 时间是接口、导出或异步任务契约的一部分时，明确携带时区，使用严格解析并校验起止范围；异步任务需要复现用户查询口径时持久化原始时区，不依赖执行节点默认时区。

## 并发与性能

- 共享可变状态必须有明确线程安全策略。多资源加锁顺序一致；锁在 `finally` 释放；`tryLock` 明确判断结果；`ThreadLocal` 在 `finally` 清理。
- 一次业务需要多个同类锁时，先去重并按稳定顺序获取，记录本次实际持有的锁；失败或完成后逆序释放，禁止释放未成功获取的锁。
- 业务线程使用项目管理的受控线程池，设置有意义的线程名、有界资源和可解释的拒绝策略；不得静默丢弃关键任务。
- 线程池公式只能作为初始估算，最终根据任务耗时、阻塞比例、下游容量、资源上限、压测和监控确定。
- 先通过指标、执行计划、Profiler 或压测确认瓶颈，再引入缓存、异步、并行或复杂数据结构。
- 时间、随机数和编号生成等不稳定因素仅在确有测试或一致性需要时提供可替换边界，同时保留简单的生产默认实现；并发编号必须明确唯一性来源和溢出行为。
- 后台扫描、清理和补偿任务同时设置单批处理上限与单次执行轮次或总量上限，达到上限后交给后续调度，避免一次任务长期占用资源。
- 工具能力选择顺序为：项目已有能力、JDK、项目已有依赖。不得仅为简单操作新增依赖或创建单方法 Util。
