# 编码与设计

本文件负责抽象边界、结构决策和设计取舍；日常落笔风格、方法编排与代码示例见[编码习惯模板](coding-habit-template.md)，两者不重复定义。

## 可读性与注释

- 类使用 UpperCamelCase，方法和变量使用 lowerCamelCase，常量使用 UPPER_SNAKE_CASE，包名使用小写；项目已有命名和外部协议字段优先。
- 抽象类使用 `Abstract`/`Base` 前缀，接口可用 `I` 前缀或名词命名，异常类以 `Exception` 结尾，测试类以 `Test`/`Tests` 结尾——均遵循项目现有约定。
- 数据对象命名遵循项目已有 `DO/DTO/BO/VO/Query/Request/Response` 边界约定，不为同构数据重复造新名。
- POJO 布尔字段避免 `isXxx` 前缀命名（避免序列化框架与 `isXxx` getter 冲突），可用 `xxx` + `isXxx()` getter。
- 禁止难懂缩写、无语义占位名及中英文混杂；业务专有名词、品牌名和外部契约命名可以沿用。
- 幂等、锁、状态机、吞异常和临时妥协必须简短说明原因。
- 当前项目已使用 Swagger/OpenAPI 时，Controller、接口方法和模型字段沿用现有注解体系；项目未使用时不主动引入。
- 优先遵循 formatter 和 Checkstyle；项目没有格式规则时以可读性为准，单行不超过 120 字符。复杂条件、泛型、链式调用和多个副作用可按语义换行。

## 简化与结构

- 不为“以后可能”增加扩展点。只有真实变化点、独立职责或明确契约才增加模式、层或 DTO。
- 一个类围绕同一职责或内聚用例集合组织。出现无关变化原因时再拆类，不以行数或操作的数据对象数量机械拆分。
- 同一业务规则尽量收口；DTO、Converter、Mapper 等边界同步变化属于正常传播，但转换逻辑应集中并检查调用方。
- 禁止新增循环依赖。维护存量系统时，不为无关需求强制重构既有循环依赖；本次改动不得通过延迟注入掩盖新问题。
- Service/DAO 是否采用 Interface + Impl，遵循项目现有结构；只有多实现、替换边界、模块契约或代理需求时新增接口。

## 集合与转换

- Stream 只用于一眼可懂的转换、过滤和收集；包含状态修改、外部调用、异常分支或多个副作用时使用普通 if/for。
- 批量输入按业务语义去空、去重或分组；响应顺序与输入相关时使用有序集合。
- 常规字段映射复用项目已有 Convert；包含业务分支、枚举选择或关联组装时使用手工转换。
- 多条件内部查询沿用已有参数对象及 Builder，只填本次需要的条件；不为单个简单查询新建 BO。
