# Java 编码习惯模板

本文件只保留日常写法和阅读习惯，不绑定某个项目的业务类、私有依赖或基础框架。

## 流程编排（第一原则）

- 入口像业务目录，从上到下呈现“校验 → 数据准备 → 核心处理 → 结果返回”。
- 入口和关键 public 方法使用连续编号注释，说明每个真实业务步骤；没有的步骤不补空壳。
  简单 Controller 委托不机械添加四步注释。
- 步骤编号是阅读目录；其他注释说明业务规则、原因、边界或妥协，不逐行翻译代码。

```java
// 1. 校验导入内容并收集错误行
// 2. 批量查询已有记录
// 3. 分别保存新增和变更记录
// 4. 返回导入结果
```

以上只示意注释写法，具体步骤按实际业务填写，不要求每个步骤都抽成方法。

- public 负责编排，private 承载完整稳定的步骤；调用者在前，辅助方法按调用顺序靠近主流程。
  重载方法相邻，不让同一业务在多个碎片方法之间反复跳转。
- 日志拼装、复杂转换和异常兜底不频繁打断主线；细节只有形成完整能力时才抽取。
- 只使用一次、表达式清晰的中间变量直接内联；表达业务含义、避免重复计算或提升可读性时保留。
  不把所有单次使用变量机械内联，也不按变量名黑名单替代语义判断。
- 用空行分隔不同逻辑块；只清理本次改动产生的无用变量、import 和注释掉的代码。

## 类与成员顺序

遵循项目已有布局约定；没有明确约定时按以下顺序组织：

1. 静态常量与 `static final` 字段。
2. 依赖字段与实例字段（private，按职责分组）。
3. 构造器。
4. public 方法，重载方法相邻。
5. protected 方法。
6. private 方法，按主流程首次调用顺序排列。
7. 必要的静态内部类。

一个类只围绕一个职责或内聚用例集合；类大不是单独拆分的理由，出现无关变化原因或独立边界时再拆。

## 排版与类型引用

- 类、字段和方法的 JavaDoc 使用多行格式，不写单行 `/** 说明 */`；方法内简短说明可用 `//`。
- 独立常量、字段、构造器和方法之间留一个空行，注释和注解紧贴所属声明；同一步骤内不机械逐句空行。
- 简短、无参数和逐项注释的枚举值放在同一行；带参数、注释或超出行宽时再按项换行，不逐项加空行。
- 注解和类型通过 import 使用短名，如 `@Resource`、`@JsonIgnore`；仅同名冲突或框架表达式需要时保留全限定名。清理本次引入的重复、无用 import。
- 只规范本次改动，不重排无关历史代码；用户要求和项目明确的格式配置优先。

```java
public enum TaskStatus {
    READY, RUNNING, COMPLETED, FAILED
}
```

## 代码模板

以下模板只表达通用结构，实际类型、注解和组件沿用项目现有能力。

### 1. Controller：校验 → Service → 返回

~~~java
public ApiResponse<Void> add(@RequestBody @Validated AddRequestDto request) {
    service.add(request);
    return ApiResponse.success();
}
~~~

### 2. Service + Impl：依赖注入 + 流程编排 + 步骤注释

~~~java
private final XxxRepo xxxRepo;

public void add(AddRequestDto request) {
    // 1. 校验并准备数据
    // 2. 保存主数据
    // 3. 处理关联数据
}
~~~

### 3. 事务方法：边界与批量落库顺序

事务注解、回滚范围和边界沿用项目现有事务配置；方法内按校验、准备、批量落库、后置处理编排。

### 4. Convert 层：自动映射与手工转换

常规字段映射复用已有 Convert；包含业务分支、枚举选择或关联组装时使用手工转换。

### 5. 查询封装：Repo + 参数对象 Builder

多条件内部查询沿用已有参数对象和 Builder，只填本次需要的条件；Repo 按条件是否存在追加查询。

### 6. 并发与锁：沿用项目现有机制

先检查锁、幂等键、唯一约束和版本控制等已有能力；具体并发正确性、线程池和锁规则见[并发与性能](concurrency.md)，本模板不重复展开。

### 7. 异常：沿用项目业务异常体系

业务校验失败使用项目已有业务异常和错误码；批量处理按项目约定收集错误或终止流程。

### 8. 日志：引用专题规则

日志格式、级别、现场信息和异常堆栈统一遵循 exception-and-logging.md，本模板不重复定义。

### 9. 工具类与常量

优先复用项目已有能力、JDK、已有依赖、常量和枚举；只有存在独立职责和稳定复用边界时才抽取公共方法或工具类。

### 10. 单元测试：行为 → 断言

测试通过 public/protected 业务入口验证业务结果、状态变化或异常，方法名表达可观察行为；Mock 只用于证明关键副作用或未发生危险调用，不替代业务断言。完整测试规则见[测试、验证与代码审查](testing-and-review.md)。

~~~java
void shouldRejectWhenBalanceInsufficient() {
    // given：准备输入与前置状态
    // when：调用业务入口
    // then：断言业务结果 / 异常 / 持久化影响
}
~~~

测试框架、Mock 方式、命名与目录沿用项目现状，不固定 JUnit 版本或模板。

## 简洁写法的边界

- 同一概念沿用已有业务词汇和动词；方法名表达真实动作，不新增含糊的 `processData`、`doXxx`。
- 简单过滤、映射和收集可用 Stream；副作用、复杂分支或外部调用用普通 if/for（完整边界见[编码与设计](coding-and-design.md)）。
- 已知非空对象直接使用，不套 `Optional.of(...).orElse(...)`（Optional 的类型边界见[Java 正确性](language-correctness.md)）。
- 在可信边界完成校验后不重复兜底；新来源或业务允许为空的数据仍按契约处理。
  不用返回空集合或默认值掩盖实际业务失败。
- 用卫语句减少深层嵌套，但不为减少缩进抽取跳板方法。
- JavaDoc 只补充签名看不出的契约和边界，不复述方法名；不主动添加类头作者、日期。

## 不复制的历史写法

即使在存量项目中看到，也不作为默认习惯继续生成：

- 为"以后可能"新增接口、策略、工厂或 DTO，但本次只有单一实现或单一调用方。
- 用 `peek`/多层 Lambda 在 Stream 里做写操作、外部调用或日志。
- 用 `Optional.of(...).orElse(...)` 包装已知非空对象，或以返回空集合/默认值掩盖真实业务失败。
- 用异常做正常流程控制，或空 `catch` 吞掉异常。
- 为减少主方法行数制造碎片方法，或补充逐行翻译式注释与无处理计划的 `TODO`。

## 变更范围风格自检

交付前检查本次全部 Java 改动：多行 JavaDoc、成员间距、短枚举单行、import 短名；既不压缩成堆，也不过度留白。纯格式修改不得改变类型绑定、字符串或业务行为；编译或格式工具不能代替此检查。
