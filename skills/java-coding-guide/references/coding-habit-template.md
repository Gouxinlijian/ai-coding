# Java 编码习惯模板

本文件只保留日常写法和阅读习惯，不绑定具体项目的业务类、依赖或框架；项目已有明确约定时以项目为准。完整正反例见[人类风格代码示例](human-style-examples.md)；其余专题规则见 SKILL.md 的按需加载表。

## 不变约束（红线）

- 不新增无职责的 Service/Manager/Facade/Strategy/Factory/Context/Handler/DTO/工具类；不为单次赋值、简单分支、参数转发、单次读写或只调用一次的两三行逻辑拆碎片方法。
- 不因无关需求删改现有日志或调整级别与打印逻辑。
- 不直接修改可重新生成的代码；只改生成源、协议、模板或生成配置。
- 不为测试扩大生产方法可见性，也不反射直测私有实现。
- 临时代码用 `TODO(负责人)：` + 处理计划，不新增无归属的裸 `TODO`。

## 流程编排（第一原则）

- 入口像业务目录：校验 → 数据准备 → 核心处理 → 结果返回。
- 入口和关键 public 方法必须有注释：真实阶段用连续编号（通常 2~5 个），简单方法一句话说明意图；每个编号下必须有实质代码，禁止空壳阶段和逐行复述；注释写业务规则，不复述代码。
- 先靠命名和空行把流程写顺，再用编号标出阶段；public 编排，private 承载完整步骤，调用者在前、重载相邻。
- 多处复用、完整业务步骤或可独立命名的职责才抽方法；单次调用且只有 2~3 行赋值、转发或一次调用，直接内联。
- 日志拼装、复杂转换和异常兜底不打断主线；单次使用的清晰中间变量直接内联；用空行分隔逻辑块，只清理本次改动的无用变量、import 和注释代码。

## 像人写的代码

- 命名承载语义：沿用项目业务词汇；变量用业务名词，集合沿用 `xxxList`/`xxxMap`；方法用业务动词（`approve`、`settle`），不用 `process`、`handle`、`result`、`data`、`info`、`temp`。
- 同一语义固定一个动词/名词，不把 `get`/`fetch`/`query`/`load` 混用，不同语义用不同词。
- 一个方法只讲一件事：按阶段用空行分段，主流程线性推进；复杂分支用卫语句提前返回，不为减少缩进抽跳板方法。
- 边界校验一次就够：入口校验后内部信任不变量，不重复判空、不层层 try-catch、不为每个方法打日志。
- 判空沿用项目写法（`== null`、`Objects.isNull` 或项目工具类），优先复用 JDK、Hutool、Apache Commons、项目 `XxxUtil`、常量、枚举、Convert、Builder。
- 简化样板：项目已使用 Lombok 时用 `@RequiredArgsConstructor` + `private final`、`@Slf4j`，字段多的对象用 `@Builder`；多 Bean 用字段级 `@Qualifier`（随 Lombok 复制到构造参数），不为此手写构造器。
- 简洁表达优先：简单二选一、链式、Stream、Optional 在一眼能懂时优先，不机械展开 if-else；有副作用、复杂分支或多步逻辑时仍用 if/for；Optional 只用于真实可能为空。
- 写法克制：Stream 只用于无副作用的转换/过滤/收集；不用 `Optional.of(...).orElse(...)` 包装已知非空对象，不用空集合/默认值掩盖失败，不用 `peek`/多层 lambda 做副作用，不用异常做流程控制，不空 `catch`。
- 不写没有信息量的代码：多余中间变量、只做一次代理的私有方法、只搬字段的 DTO/Convert、没有需求支撑的接口/策略/工厂一并去掉。
- 注释解释“为什么”和业务规则，不复述代码；自解释的 getter/setter、重写方法和显而易见的赋值不写注释；读起来像一段业务说明。

## 类与成员顺序

常量 → 依赖字段 → 构造器 → public → protected → private（按调用顺序）→ 内部类；项目已有布局优先。依赖字段用 `private final`，字段之间空行；一个类围绕一个职责，类大不是拆分理由。

## 排版与类型引用

- 方法（尤其 private）用多行 JavaDoc 说明职责；字段用一行 `/** 说明 */`；简单 getter/setter 可省略。不复述签名，不写作者、日期。
- 短枚举可单行；类型通过 import 使用短名；只清理本次引入的重复、无用 import。
- 单行优先：能一行完整表达就保持一行，不为“整齐”主动折行；单个调用的唯一实参、单个 `.set()` 节点、单层赋值不拆到下一行。
- 链式与 Stream：1~2 个调用的短链一行；3 个以上每个 `.method()` 一行、缩进对齐；单行 lambda 省大括号，多行 lambda 换行并保留大括号。
- 项目没有格式规则时，单行上限 160 字符；日志调用不超过 160 字符就整行写完，不按参数个数折行；超过 160、多个独立链式节点、多行 lambda、集合字面量或需分组的复杂条件才换行，超长优先抽局部变量。
- 只规范本次改动，不重排无关历史代码。

```java
// 反例
entity.setRemark(
        StringUtils.defaultString(vo.getRemark()));

// 正例
entity.setRemark(StringUtils.defaultString(vo.getRemark()));
```

## 代码模板

- Controller：边界校验、调用 Service、返回项目协议；能一行委托就一行。
- Service：Lombok 项目用 `@Slf4j` + `@RequiredArgsConstructor` + `private final`，否则用现有注入；按阶段编排并加编号注释。
- 事务：沿用项目 `@Transactional`；事务内只做本地原子写，RPC/MQ/文件放事务外。
- Repo/DAO：沿用项目 `Repo`/`Mapper`/`BaseServiceImpl`、Wrapper 和参数 Builder，只查需要的列和条件。
- 数据对象：新增 PO/DTO/VO/BO 后缀大写、每个业务字段一行注释；Lombok 项目字段多用 `@Builder`。
- Convert/异常：同构（字段名与类型一一对应、无计算/枚举/关联）用 `BeanUtil` 或 `XxxConvert`，否则手工转换，逐方法判定、不整类手写；JSON 快照、金额、状态赋值、正负号、聚合计数属手工转换并在 JavaDoc 说明；异常用项目业务异常和错误码枚举。
- 日志/工具：日志格式和关键节点遵循[异常、日志与可靠性](exception-and-logging.md)；工具、常量、枚举优先复用项目能力。
- 单元测试：通过 public 入口验证业务结果，方法名表达可观察行为，Mock 不替代业务断言；详见[测试、验证与代码审查](testing-and-review.md)。

## 变更范围风格自检

交付前检查本次全部 Java 改动：

- 格式：多行 JavaDoc、成员间距、短枚举单行、import 短名、单行优先（无意义折行）；不压缩成堆，也不过度留白。
- 方法能否一句话说清？删掉注释后主流程是否仍能读懂？注释是否讲业务规则而不是逐行复述？变量名是否带业务含义？有没有可删的中间变量、转发方法或重复判空？
- 私有方法是否都有 JavaDoc？字段注释是否齐全？新增 DTO/VO/BO/PO 后缀是否大写？构建/映射是否优先用 Builder/Convert/BeanUtil？
- 有没有只调用一次的碎片方法？关键分支、提前返回、状态流转和异常是否有 INFO 日志？
- 有没有用不到的枚举值、错误码、字段或配置项？预留代码一律删掉。
- 时间来源、计数规则、删除级联是否与开工前定义的口径一致？

纯格式修改不得改变类型绑定、字符串或业务行为；编译或格式工具不能代替以上检查。
