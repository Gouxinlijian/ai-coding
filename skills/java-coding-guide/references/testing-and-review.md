# 测试、验证与代码审查

## 测试设计

- 测试应自动、独立、可重复，不依赖执行顺序、真实时间等待或不稳定的外部环境。
- 测试方法名优先表达可观察行为和条件，例如 `shouldRejectXxxWhenYyy`、`shouldKeepXxxWhenYyy`，避免只复述被测方法名。
- 测试断言业务结果、状态变化、持久化影响或异常行为；禁止空断言、只执行不校验，或仅验证 Mock 调用次数。
- `verify(..., never())` 只在证明越权、校验失败、锁竞争等场景没有发生危险写入或外部副作用时使用，并与业务断言配合。
- 覆盖正常路径、边界值、非法输入和重要失败路径。核心业务规则与高风险分支必须覆盖，不以固定覆盖率数字替代有效测试。
- 状态机、重试、时间转换、编号生成等纯规则使用小而完整的矩阵测试覆盖允许、拒绝、边界、幂等和上限行为。
- private 方法通过 public/protected 业务入口间接覆盖；禁止为测试扩大生产代码可见性或使用反射测试实现细节。
- 公共接口存在注解、请求体类型、泛型返回值或序列化结构等编译器无法保护且容易被误改的兼容契约时，可以增加契约测试；不为普通 Controller 机械添加反射测试。
- 时间、随机数、外部系统和并发调度应有稳定边界，但不为简单代码增加多余抽象。
- 测试框架、目录、命名、Mock 方式和集成测试策略沿用项目现状，不固定 JUnit 版本或模板。

## 何时补测试

- 修改业务规则、边界条件、错误处理、事务、并发、序列化或已存在测试覆盖的行为时，同步新增或更新相关测试。
- 纯格式、注释、生成文件或能够由编译器/静态检查完全覆盖的低风险机械修改，可以不新增测试。
- 若测试需要大规模重构公共测试基础设施、引入新依赖或访问真实外部环境，先说明范围并询问用户。

## 验证

- 先确定与改动匹配的最小验证方案，但不得主动运行编译、测试或构建命令。应说明推荐命令、验证目的和预期影响，并在获得用户明确确认后再执行。
- Maven `-pl ... -am ... test` 会构建选中模块及其上游依赖模块，属于多模块 Reactor 构建，不视为快速定向测试，执行前先询问用户。
- 发现 POM 或构建参数跳过测试时，报告测试未执行的原因和实际验证结果；不得自动添加或修改 `-DskipTests=false`、`-Dmaven.test.skip=false` 等开关重跑，先询问用户。
- 执行全量测试、`mvn package`、`mvn install`、预计耗时较长或会访问外部环境的命令前，先询问用户。
- 优先使用项目已有 wrapper、构建配置和 CI 同款命令。验证失败必须报告命令、关键错误和未完成项。
- 定向检查通过后，只有新增修改、失败或未解决风险需要时才扩大验证范围。

## 代码审查顺序

按以下优先级给出可操作问题，格式类问题主要交给 formatter、Checkstyle 和 CI：

1. 正确性：空值、边界、状态转换、异常语义、资源释放。
2. 数据一致性：事务、唯一约束、幂等、消息与数据库一致性。
3. 并发：竞态、锁、线程池、上下文传播、任务丢失和重复执行。
4. 安全：权限、注入、敏感信息、反序列化和依赖风险。
5. 兼容性：公共 API、DTO、枚举、数据库、消息、缓存和旧消费者。
6. 性能：N+1、循环 I/O、执行计划、资源上限和可观测证据。
7. 可维护性：主线是否清楚、职责是否内聚、抽象是否必要、命名和注释是否准确简短。

审查结论必须关联具体文件和行号，说明触发条件、后果和可行修复方向。没有发现问题时明确说明剩余测试缺口或风险。
