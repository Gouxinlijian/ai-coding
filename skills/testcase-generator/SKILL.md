# 测试用例生成

## 启用条件（硬性）

只有用户显式点名本技能才执行本流程，点名方式包括：

- 说“用 testcase-generator”“使用测试用例生成器技能”“加载 testcase-generator skill”；
- 直接调用 `/testcase-generator`。

用户仅表达测试相关需求（要测试用例、要测试点、要 xmind、要测试方案）但没有点名本技能时，不加载、不套用本流程，按普通任务处理，并可一句话询问是否启用本技能。

启用后只做测试用例交付；代码修改、环境部署、缺陷修复等不属本技能范围，遇到时说明并交回主流程。

## 目标

交付“与真实业务一致、覆盖范围符合用户选择、格式符合用户选择”的测试用例，且每条业务规则、字段、状态都能追溯到证据来源。

## 适配原则

- 不绑定业务域、技术栈、目录结构或知识库平台：先探测当前项目实际情况，再按本流程执行。
- 文中出现的接口、菜单、数据模型、造数、影响面等只是“能力类别”，具体工具、命令与目录以当前环境实际提供的为准。
- 降级链：知识检索问答 → 代码与配置 → 需求文档与既有用例 → 向用户确认。
- 文中的业务名词、目录名仅为说明性示例，不要求当前项目与之相同。

## 三个门禁

| 门禁 | 通过条件 | 未通过时 |
|---|---|---|
| 一、产出确认 | 输出格式、用例粒度、覆盖范围、交付位置已由用户确认 | 继续提问，不生成 |
| 二、业务确认 | 业务理解确认单已建立，无阻塞级未确认项，用户已过目 | 列出缺口向用户提问，不生成 |
| 三、交付自检 | 按“自检清单”核对完成，未覆盖项已如实报告 | 补齐或如实标注，不隐瞒 |

门禁任一未通过时，停在该步骤并说明卡在哪里，不输出“占位版”“示意版”“示例版”用例。

## 执行流程

### 步骤 1 产出确认

按 `references/intake.md` 分批提问：一次最多 4 个问题，最多 2 轮。

- 第一轮必问：输出格式（md / xmind / 两者）、用例粒度（表格用例 / 测试点清单 / 精简断言表 / 两者）、覆盖范围（功能、接口、UI、兼容、性能、安全）、交付位置。
- 第二轮只问第一轮未覆盖且影响产出的项：变更类型（新功能 / 已有功能变更）、需求来源与版本、范围边界（哪些明确不做）、角色权限、测试环境与账号、历史用例复用。
- 用户回答“你决定/随便/都行”时采用 `references/intake.md` 的默认值，并在交付说明中写明用了哪些默认。
- 需求来源不明确（文档、链接、代码模块、页面地址都没给）时先问清，不自行假设。

### 步骤 2 业务摸底（生成前必须完成）

按 `references/business-grounding.md` 执行：先探测当前项目形态（仓库类型、构建与依赖文件、文档目录、已有用例、可用的检索工具），再按“知识检索 → 本地代码与配置 → 需求文档”取证，并产出业务理解确认单。

- 知识检索：当前环境若提供知识库类检索服务（如具备能力探测与问答入口的 MCP），先用其能力探测确认能回答的范围，再按能力类别提问——接口契约、菜单与页面、数据模型与字段、变更影响面、造数前提、需求原文；已知精确定位信息时才做定点精读，不要用关键词检索工具传自然语言问句。没有这类服务或能力不支持时跳过，直接走代码与文档。
- 本地证据：项目代码与配置（仓库有 `.codegraph/` 时优先 CodeGraph，否则用通用文本检索定位入口、路由、校验、状态与 SQL）、`docs/` 下已有文档、需求文档（在线文档链接优先用对应读取工具，读不到就请用户提供正文）。
- 跨模块、跨端项目必须分部分取证：同一交付物可能同时涉及后端服务、前端应用、移动端、批处理或数据任务，各部分的入口、返回结构、校验位置、权限来源都可能不同，不得用一部分的结论套其他部分。
- 变更类需求先锁定影响面：直接改动的接口与页面、同链路的上下游、被复用的公共组件或工具类，据此圈定回归范围，不重写全量用例。
- 证据分级：A 为直接证据，B 为多源推断，C 为无证据。C 级内容不得写入用例的预期结果。
- 阻塞判定：核心链路缺证据、规则互相矛盾、范围说不清时，停下来向用户提问，列出具体缺口。

### 步骤 3 设计用例

按 `references/design-methods.md` 选择方法，只选与本次需求匹配的：

| 需求特征 | 方法 |
|---|---|
| 输入有格式、长度、枚举限制 | 等价类划分 + 边界值 |
| 多个条件组合决定结果 | 决策表 |
| 有审核、发布、流转等状态 | 状态转换（含非法流转） |
| 有端到端业务流程 | 场景法（主流程 + 备选流 + 异常流） |
| 有历史缺陷、经验型风险 | 错误推测 |
| 已有功能的小范围变更 | 回归选测（按影响面分级，不全量重写） |

不为凑方法生成用例；同一测试点被多个方法覆盖时合并为一条。

### 步骤 4 生成交付物

按 `references/output-templates.md` 输出：

- Markdown 默认写入 `docs/local/{业务范围}/`；项目已有测试用例目录或任务交付目录时，按其实际结构落盘，不新造目录。文件名 `{需求名}-测试用例[-vMMdd_HHmmss].md`，同名文件已存在时追加时间戳保留旧版本，不覆盖。
- XMind 用脚本从 Markdown 转换：`python {SKILL_DIR}/scripts/md_to_xmind.py <input.md> <output.xmind> [标题] [--tables expand|skip]`。表格默认展开为节点，只要标题与列表时用 `--tables skip`。脚本失败时报告错误并保留 Markdown，不伪造 xmind。
- 用例编号 `TC-{模块}-{序号}`，同一交付物内唯一。
- 每条用例带追溯字段：对应需求条款、接口路径或规则 ID。
- 预期结果按模块实际返回体和校验行为写，不按习惯写法统一成一种返回结构。

### 步骤 5 自检与交付

先按本文件末尾“自检清单”核对，再输出交付说明：

1. 业务理解确认单摘要与证据来源（知识库、代码、文档分别用了什么）。
2. 用例数量及按模块、优先级、范围的分布。
3. 实际生成的文件路径与格式。
4. 未覆盖项、待确认项及原因。
5. 采用了哪些默认值。
6. 按模块、端或技术栈说明取证差异（入口、返回结构、校验位置、页面与权限来源），以及由此产生的假设。

不报无法验证的覆盖率百分比；覆盖情况用“已覆盖的功能点、业务规则、状态流转、异常分支清单”表达。

## 自检清单

- [ ] 用户显式点名本技能后才启动
- [ ] 输出格式、粒度、范围、交付位置均已确认
- [ ] 业务理解确认单已建立，用户已过目
- [ ] 预期结果中不含 C 级（无证据）内容
- [ ] 功能点、业务规则、状态流转、异常分支都有对应用例
- [ ] 跨模块、跨端项目的预期结果按各部分实际行为分别写
- [ ] 变更类需求已按影响面锁定范围，没有全量重写
- [ ] 用例编号唯一，步骤可执行，预期结果可判定
- [ ] 同时输出 md 与 xmind 时两者内容一致
- [ ] 未覆盖项与未确认项已如实列出

## 常见错误

| 错误 | 处理 |
|---|---|
| 用户提到“测试用例”就自动执行本技能 | 只有显式点名才启用 |
| 需求含糊就直接套通用模板生成用例 | 回到步骤 1 提问 |
| 知识库没答案就凭经验补字段或规则 | 列为未确认项，向用户提问 |
| 用关键词检索工具传自然语言问句 | 改用能力探测后的问答入口 |
| 拿代码里的类名猜表名、接口字段 | 查实体注解、SQL、接口文档或知识库 |
| 用一部分的返回体或校验风格套其他部分 | 分部取证，按实际行为写预期 |
| 需求只是变更却重写全量用例 | 先取影响面，再圈定回归范围 |
| 把造数结果或真实业务数据贴进用例 | 只写数据要求与字段取值，不贴真实数据 |
| 报“覆盖率 95%”但没有覆盖清单 | 改为列清单，不报百分比 |
| 直接覆盖同名用例文件 | 加时间戳生成新版本 |
| 用户没选的范围也生成一堆用例 | 只生成用户确认的范围 |
