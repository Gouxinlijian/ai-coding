# 业务摸底与确认

测试用例的预期结果只能来自证据。本步骤在生成用例之前完成，未完成不进入生成。

## 一、摸底顺序

按以下顺序取证据，前一步能闭环就不重复查：

1. **知识检索（当前环境有时优先）**：业务规则、接口契约、菜单与页面、数据表与字段、服务拓扑、造数前置条件；没有该服务时直接进入下一步。
2. **项目代码与配置**：接口定义、校验逻辑、状态枚举、SQL、权限配置、消息与定时任务。
3. **需求文档与历史材料**：需求文档、原型、接口文档、缺陷记录、既有测试用例。
4. **用户补充**：前三步查不到且影响用例预期结果时，向用户提问。

## 二、知识检索（当前环境提供时才用）

先探测当前环境是否提供知识库检索服务：可能是一个 MCP、一个命令行工具或一个内部 Web 服务，也可能完全没有。没有或能力不支持时，跳过本节，直接走“三、本地证据”，不硬查、不编造。

| 能力类别 | 用法 | 没有该能力时 |
|---|---|---|
| 能力探测 | 先确认平台能回答哪些类型的问题 | 按经验列提问清单，用代码查证 |
| 自然语言问答 | 默认入口，一次问一个问题，用业务问句 | 用代码与文档检索替代 |
| 关键词/结构化检索 | 已知来源或标识时取原始证据，不传自然语言问句 | 用通用文本检索 |
| 定点精读 | 已知来源与定位信息时展开或翻页 | 直接读取文件 |

中文业务词与代码标识不一致时，补充精确标识一起问，不自行发明标识。

摸底阶段要反复提问覆盖以下几类问题（按本次需求取舍）：

- 这个功能属于哪个系统、哪个菜单、哪个页面对应哪个接口？
- 业务规则是什么：谁能操作、什么状态可操作、有哪些必填和校验、金额和数量怎么算？
- 数据存在哪张表、关键字段是什么、枚举值分别代表什么？
- 有哪些状态、怎么流转、哪些流转被禁止？
- 有哪些前置依赖：其他服务、消息、定时任务、外部系统？
- 造数需要什么前置数据？

调用结果不足以回答时，换问法再问一次；仍不足则转为代码检索或向用户提问。不得用“通常是”“一般是”补答案。

### 按能力类别取证

平台若提供分类能力标识，可把问题限定到对应类别；只把下面的标识当示例，实际名称以当前平台为准：

| 要查什么 | 能力类别（示例标识） | 典型问法 |
|---|---|---|
| 接口契约 | 接口分析（如 `api_analysis`） | 某个页面提交时调用的接口路径、入参、返回结构、错误码是什么 |
| 菜单与页面 | 菜单导航、前端导航（如 `menu_knowledge`、`frontend_navigation`） | 这个功能在哪个菜单下、对应哪个路由和页面文件 |
| 数据模型与字段 | 数据库结构（如 `database_schema`） | 这张表有哪些字段、枚举值、必填与长度限制 |
| 变更影响面 | 版本差异、变更影响（如 `git_diff`、`change_impact_analysis`） | 这次改动影响哪些接口、页面和上下游 |
| 造数前提 | 造数计划（如 `test_data_planning`） | 构造一条满足前置条件的数据需要哪些依赖 |
| 需求原文 | 文档检索（如 `document_search`） | 需求文档里这条规则是怎么写的 |

平台若提供造数计划或影响面分析（示例：`action=test_data`、`action=change_impact`），优先用它拿结构化结果；这类能力通常只产出计划或合成数据，不读写业务库、不执行测试。没有对应能力时，用代码、配置与文档自行梳理。

### 造数前置

用例依赖特定数据时，在确认单中单列造数要求，只写字段与取值，不贴真实业务数据：

| 实体/表 | 关键字段 | 取值要求 | 数量 | 用途 |
|---|---|---|---|---|
| | | | | |

先用知识检索或数据库结构确认真实表与字段；没有这类服务时查 DDL、实体映射或接口文档，不要把假设字段直接写进用例前置条件。

## 三、本地证据

- 仓库根有代码图谱索引（如 `.codegraph/`）且工具可用时，用它做符号定位与调用链分析；否则用通用文本检索定向查找入口、路由、校验、状态与 SQL。
- 接口契约以接口定义或接口文档为准；字段约束用服务端校验、数据库定义与前端校验交叉验证。
- 表名以实体映射、ORM 元数据、SQL、迁移脚本为准，不从类名直接推断。
- 需求文档是链接时用对应的读取方式获取；抓不到内容时说明失败，请用户提供正文或截图。
- 已有用例在 `docs/local/`、项目既有用例目录或指定目录时先读，沿用既有编号与风格，不重复造轮子。

### 跨模块、跨端项目

- 先确定需求落在哪些部分：后端服务、前端应用、移动端、批处理或数据任务，各自可能有独立的入口、返回结构、校验位置和权限来源。
- 同一系统内不同部分的实现风格可能完全不同（例如一部分有统一返回包装、另一部分直接返回实体；一部分集中校验、另一部分分散校验），必须分别取证。
- 前端调用地址以请求封装、环境变量或配置为准，不按后端路径硬拼；菜单与按钮权限可能由服务端下发，也可能在前端静态定义，以实际加载链路为准。
- 预期结果按各部分的实际行为写；交付物跨部分时在追溯列注明所属模块或端。

### 变更类需求：先取影响面

需求是“已有功能的一次变更”时，从影响面开始摸底，不从需求全文重头分析：

1. 取变更证据：提交、分支差异或版本变更清单；环境有变更影响面分析能力时优先用（示例标识 `git_diff`、`change_impact_analysis`），没有则用版本控制命令定位。
2. 分三级圈定范围：直接改动（改动的接口与页面）、同链路（调用方、下游、消息、定时任务）、共用能力（公共组件、工具类、字典与枚举）。
3. 只对三级的交集出回归用例；未受影响的功能写“本次未涉及”，不重复生成。
4. 影响面无法确认时向用户索要变更清单，不按“可能都影响”全量重写。

## 五、证据分级

| 等级 | 含义 | 能否写进预期结果 |
|---|---|---|
| A | 知识库、代码、文档中的直接证据 | 能 |
| B | 多处证据推断，且结论唯一 | 能，但需在用例追溯栏标注“推断” |
| C | 无证据，仅凭经验或常识 | 不能 |

## 六、阻塞判定

出现以下任一情况，停止生成并向用户提问：

- 核心链路（入口、规则、状态、字段）存在 C 级内容，且直接影响预期结果；
- 需求文档与代码行为矛盾，无法判断以哪个为准；
- 范围边界不清，无法确定哪些功能要出用例；
- 无法确定角色权限差异，而需求涉及多角色；
- 用户要求的产出格式或路径无法落地（如目录不可写、xmind 转换工具缺失）。

提问时一次性列出全部缺口，每条缺口写清“缺什么、影响哪些用例、需要用户提供什么”，不发散追问。

## 七、常见错误

| 错误 | 处理 |
|---|---|
| 用类名、方法名猜接口路径和表名 | 查路由注解、接口文档、SQL |
| 把前端提示文案当成业务规则 | 追到后端校验或规则配置确认 |
| 知识库有相似历史结论就直接复用 | 核对版本与环境，不跨版本套用 |
| 一个字段查不到就整段跳过 | 列入未确认项，影响预期结果时提问 |
| 用一个模块的返回体套所有模块 | 分模块确认入口前缀、返回体与校验风格 |
| 变更需求按“可能都影响”全量重写 | 先取影响面，只覆盖直接改动、同链路、共用能力的交集 |
| 把造数结果或真实业务数据写进用例 | 只写字段与取值要求，不贴真实数据 |
| 一次发十几个问题给用户 | 归并为“缺口清单”，一次问完 |
| 摸底没做完就开始写用例 | 回到本步骤，先过门禁二 |
