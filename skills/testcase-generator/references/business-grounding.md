# 理解业务（内部步骤）

目标：在生成用例前，把需求文档里的页面与交互整理成可执行的清单。本步骤的产出自用，不作为交付物输出。

## 一、从需求文档开始

拿到文档后先通读，按页面整理下面这张表（内部使用）：

| 页面 | 入口（菜单/按钮） | 功能点 | 关键交互 | 需求原文位置 |
|---|---|---|---|---|
| | | | | |

提取时固定关注：

- 页面清单：本次需求涉及哪几个页面、新增还是改造。
- 字段与控件：输入框、下拉、单选多选、日期、上传、只读、默认值、必填。
- 校验与提示：什么条件下报错、提示文案是什么、提示出现在哪里。
- 按钮与状态：哪些按钮在什么状态可用、禁用、隐藏；主次操作。
- 流程与跳转：提交后去哪、返回是否保留状态、是否需要二次确认。
- 列表与搜索：列有哪些、默认排序、筛选条件、空结果表现。
- 权限与可见性：不同角色看到什么、无权限时的表现。

需求没写清的，先标记为“待确认”，不要自行补规则。

## 二、补齐缺失细节

默认只依据需求文档。文档写清楚的功能直接进入设计，不需要额外查代码。

只有以下情况才查代码，且必须先拿到用户提供的代码地址：

- 用户勾选了接口层；
- 用户明确要求用例对齐页面实现（例如确认控件类型、校验文案、按钮禁用条件）。

拿到代码地址后按顺序补齐：页面文件（字段标签、控件、校验、提示、跳转）→ 接口定义（取值范围、枚举、必填、长度，不因此写成接口用例）→ 知识检索（环境提供时才用）。

没勾选接口层、也没给代码地址时，不要自行检索用户未提供的仓库；文档没写清且影响预期结果的细节，列成缺口一次性问用户。

跨端项目要分开确认：管理端页面、移动端页面、批处理任务的表现可能不同，不能互相套用。

## 三、变更类需求

需求是改已有功能时，先确认改动范围：

1. 改了哪些页面与功能。
2. 同页面内相邻功能是否受影响（共用组件、共用字典、共用权限）。
3. 是否需要回归已审核、已提交等历史数据路径。

只覆盖受影响范围，不重写全量用例；影响面说不清时向用户要变更说明。

## 四、证据使用规则

- 内部记录来源（需求章节、页面文件、接口定义），便于自查与回答追问。
- 交付物中不出现证据表、代码行号、需求编号、影响级别标签。
- 无依据的内容不写入预期结果；必须写时标注“待确认”并向用户提问。
- 不把真实账号、令牌、客户资料写进用例。

## 五、阻塞条件

出现以下情况停下来问用户，不生成：

- 没有需求文档，且用户也说不清页面与功能。
- 需求与页面实现矛盾，无法判断以哪个为准。
- 关键交互（校验、提示、按钮状态、跳转）缺失且影响预期结果。
- 角色权限差异说不清，而需求涉及多角色。

## 六、常见错误

| 错误 | 处理 |
|---|---|
| 拿代码反推需求，把实现当业务规则 | 以需求文档为准，实现差异单独向用户确认 |
| 需求一句话就开始补细节 | 追问页面与交互，或请用户补充文档 |
| 把接口字段清单当功能清单 | 回到页面视角，写用户能看到和操作的内容 |
| 猜测提示文案和跳转目标 | 查页面文案或向用户确认 |
| 把内部取证表输出到交付物 | 只保留用例主体与覆盖说明 |
| 需求与实现冲突时默认按实现写 | 按需求写，冲突点在交付说明中提示 |
