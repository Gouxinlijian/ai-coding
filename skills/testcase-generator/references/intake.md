# 产出确认提问单

## 提问规则

- 用 `ask_followup_question` 批量提问，一次 1～4 题，每题 2～4 个选项；选项带一句说明。
- 最多 2 轮。第二轮只问“影响产出且第一轮未覆盖”的项。
- 用户已在需求描述里说清的项不重复问。
- 用户回答“你决定 / 随便 / 都行 / 你看着办”时，采用本文件默认值，并在交付说明中写明。
- 问题不预设倾向，不把“全部都要”作为默认勾选。
- 范围类问题用多选，格式与粒度类问题用单选。

## 第一轮（必问）

### Q1 输出格式（单选）

| 选项 | 说明 |
|---|---|
| Markdown（默认） | 交付单个 `.md` 文件，便于评审、版本管理和后续转格式 |
| XMind | 只交付 `.xmind` 思维导图，适合按节点评审和执行 |
| 两者都要 | 先生成 Markdown，再用脚本转 xmind，内容一致 |

### Q2 用例粒度（单选）

| 选项 | 说明 |
|---|---|
| 表格用例（默认） | 一行一条用例，含前置条件、步骤、预期结果、优先级，适合执行与缺陷跟踪 |
| 测试点清单 | 按“模块 → 子功能 → 功能点 → 测试点 → 验证项”的勾选清单，适合需求评审与验收打勾 |
| 精简断言表 | 两列「用例 / 断言」，适合任务目录内快速核对，不追求执行细节 |
| 两者都要 | 清单作为覆盖矩阵在前，表格作为执行用例在后 |

### Q3 覆盖范围（多选）

| 选项 | 说明 |
|---|---|
| 功能 | 业务规则、流程分支、状态流转（默认建议勾选） |
| 接口 | 入参出参、状态码、幂等、重复提交、异常码 |
| UI 与交互 | 页面元素、表单校验提示、加载态、空态、弹窗 |
| 兼容 | 浏览器、分辨率、终端、系统版本 |
| 性能 | 并发、响应时间、大数据量、超时 |
| 安全 | 越权访问、注入、敏感信息展示、脱敏 |

用户未勾选的范围不生成用例，也不在交付物中保留“未覆盖”占位章节。

### Q4 交付位置（单选）

| 选项 | 说明 |
|---|---|
| `docs/local/{业务范围}/`（默认） | 业务范围按需求所属领域命名，与项目实际业务一致 |
| 项目已有用例目录 | 沿用项目现有的测试用例存放目录（示例：`docs/testcase/`），便于与历史用例、导图放一起 |
| 项目任务交付目录 | 项目按任务、需求单或迭代管理交付物时，跟随该任务目录（示例：`docs/ai-tasks/{任务ID}/`） |
| 指定目录 | 用户给出路径，写入该路径 |
| 直接输出到对话 | 不落盘，只在对话中给出用例正文 |

交付位置影响文件名与路径，必须在生成前确定；项目已有约定时优先沿用，不另建目录。

## 第二轮（按需，只问缺失项）

| 问题 | 触发条件 | 提法 |
|---|---|---|
| 变更类型 | 未说明是新功能还是改已有功能 | 这是新功能上线，还是已有功能的一次变更？变更是哪次提交、哪个版本？ |
| 需求来源与版本 | 未给文档、链接、代码模块或页面地址 | 需求的准确来源是什么？是哪个版本或哪次变更？ |
| 范围边界 | 需求只说“做某功能”，没说做到哪里 | 本期明确不做的部分有哪些？哪些属于后续迭代？ |
| 角色与权限 | 功能涉及多角色或数据权限 | 涉及哪些角色？各角色可见、可操作的范围有差异吗？ |
| 测试环境与账号 | 用例需要真实环境执行 | 在哪个环境执行？账号、测试数据是否已有？ |
| 历史用例复用 | 该模块可能已有用例 | 是否已有用例？是合并更新还是重新生成？ |
| 优先级分层 | 用户对交付节奏有要求 | 是否需要区分 P0～P3？P0 的判定标准是什么？ |
| 造数前置 | 用例依赖特定业务数据才能执行 | 是否需要单独列出造数要求（实体、字段、状态、数量）？ |

## 不该问的问题

- 需求文档或知识库已有明确答案的（自行查证，不要转嫁给用户）。
- 技能内部约定的事项：用例编号规则、表格列结构、xmind 层级、文件命名格式。
- 与本次交付无关的环境细节、技术实现细节、排期问题。
- 已经是用户明确指令的内容（重复确认会消耗耐心）。
