# 输出模板

只输出用户勾选的范围。交付物只含用例主体与简短覆盖说明，不放内部过程材料。

## 一、文件与命名

| 项 | 规则 |
|---|---|
| Markdown 路径 | 默认 `docs/local/{业务范围}/{需求名}-测试用例.md`；项目已有用例目录或任务目录时按其结构落盘 |
| 版本文件 | 同名已存在时改为 `{需求名}-测试用例-v{MMdd_HHmmss}.md`，不覆盖 |
| XMind 路径 | 与 Markdown 同目录同名，扩展名 `.xmind` |
| 文档标题 | 首行 `# {需求名} 测试用例` |
| 语言 | 中文；页面字段名、按钮文案保留页面原文 |

## 二、默认结构：功能场景清单

这是默认格式，同时适用于 Markdown 与 XMind：

```markdown
# {需求名} 测试用例

## {页面名称}

### {功能名称}

#### {场景名称}

- 操作：{用户在页面上做什么}
- 预期：{页面上看到什么结果}
```

示例：

```markdown
## 客户主体维护

### 新增客户时填写结算主体

#### 选择单个结算主体后保存

- 操作：在客户主体维护页点击新增，填写必填项，结算主体选择“主体A”，点击保存
- 预期：保存成功并提示“保存成功”，列表新增该记录，结算主体列显示“主体A”

#### 结算主体留空后保存

- 操作：结算主体不选择，其余必填项填写完整，点击保存
- 预期：提示“请选择结算主体”，弹窗不关闭，已填内容保留
```

约束：

- 页面名称用用户能看到的菜单或页面标题。
- 功能名称写“做什么”，不写模块代号。
- 场景名称写“什么条件下测什么”。
- 一个场景最多 1～3 条操作、1～3 条预期，过长就拆成多个场景。
- 不在任何节点出现编号、优先级角标、证据代号、影响级别。

## 三、可选结构：表格用例

仅在用户需要执行跟踪或缺陷管理时使用，且只交付 Markdown（不要用表格生成 xmind）。

```markdown
| 编号 | 页面 | 功能 | 场景 | 前置条件 | 操作步骤 | 预期结果 | 优先级 |
|---|---|---|---|---|---|---|---|
| 1 | 客户主体维护 | 新增客户 | 结算主体留空保存 | 已登录有新增权限 | 不选主体，填完必填项后保存 | 提示“请选择结算主体”，弹窗不关闭 | P1 |
```

- 编号在本文件内从 1 递增即可，不使用 `TC-模块-序号` 之类的内部编码。
- 优先级列只在用户要求时出现。
- 表格版本与清单版本内容必须一致，不能一套一个说法。

## 四、XMind 结构

```text
{需求名} 测试用例
├── 客户主体维护            ← 页面
│   ├── 新增客户            ← 功能
│   │   ├── 选择主体后保存   ← 场景
│   │   │   ├── 操作：...
│   │   │   └── 预期：...
│   │   └── 主体留空后保存
├── 覆盖说明
└── 未覆盖
```

转换命令：

```bash
python {SKILL_DIR}/scripts/md_to_xmind.py <input.md> <output.xmind> "{需求名}"
```

- 清单结构直接转换，不需要额外参数。
- 转换后核对节点数，并抽查 2～3 个场景的层级是否挂在正确的功能下。
- 失败时保留 Markdown，原样报告错误，不声称已生成 xmind。

## 五、覆盖说明

放在用例主体之后，保持简短：

```markdown
## 覆盖说明

| 页面 | 覆盖功能 | 说明 |
|---|---|---|
| | | |

## 未覆盖

| 项 | 原因 |
|---|---|
```

- 只写页面、功能、未覆盖原因，不写设计方法、证据来源、影响级别、执行约定。
- 没有未覆盖项时写“无”，不删除该章节。

## 六、禁止出现的章节与内容

- 基本信息、执行约定、优先级说明、影响级别说明。
- 证据与业务理解确认单、代码行号引用、需求条款编号。
- 测试数据准备清单（用户明确要求时可单独提供，不默认输出）。
- 造数账号、真实业务数据、令牌。

## 七、交付前自查

- 每个场景都能对应到需求里的某个功能或交互。
- 任意抽取三个节点，能一眼看出测的是哪个页面、什么操作、期望什么结果。
- 没有编号、角标、内部代号。
- Markdown 与 XMind 内容一致。
