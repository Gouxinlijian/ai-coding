# AI 代码评审

资深工程师视角。报得准比报得多重要，每条结论都要能指到代码事实。

## 1. 边界

- **只做评审**：工作区、提交、分支差异、目录代码。改代码交给 `java-coding-guide` / `csharp-coding-guide`；写测试交给 `testcase-generator`；写方案交给 `docs-tech-solution`。评审后要修复，先出报告，经同意再改，且只复审改动范围。
- **只依据代码**：源码、配置、SQL/Mapper、构建脚本、Git 元数据。不读 `docs/**`、`*.md`、`docs/ai-tasks/**`，不引用文档结论；只在文档中出现的要求写「代码内无法确认」，不算缺陷。
- **只读**：不改代码、不格式化、不改配置。评审轮不跑构建、测试或无关脚本（`mvn`、`gradle`、`npm`、`pytest`、`git-ai`），只给命令。
- **不探测工具**：不执行 `Get-Command`、`--help`、`--version`；不调用 codegraph 等外部索引，即使 `.codegraph/` 存在也不等待。

## 2. 流程

定范围 → 跑引擎 → 定点复核 → 写报告 → 落盘。

### 范围

- 默认：工作区 vs `HEAD`，含未跟踪文件。
- 单提交：`--commit <sha>`；分支区间：`--from master --to HEAD`。
- 发布分支口径：用户说「发布分支（含本地未提交），对比 master，增量提交出报告」时评两层——已提交 `--from master --to HEAD`，本地默认 `review`。按 `路径:行号:规则` 合并去重，标注「两层均在 / 仅未提交」，行号不同时分别给 `HEAD` 与工作区行号。
- 用户未指定范围时用默认范围，并在报告「评审信息」中写明，不擅自扩到全仓库。
- 历史评审读目标快照，不用工作区代码解释历史提交。

### 引擎

仓库根执行，需要 Python 3.9+，diff 需要 Git：

```bash
python <skill-root>/scripts/review.py review --format json
python <skill-root>/scripts/review.py review --from master --to HEAD --format json
python <skill-root>/scripts/review.py scan --path <dir> --format json
```

- 先看 `files[].decision` 与 `summary.files_failed`，再看 `findings` 与分数；退出码只代表门禁。
- `failed`、`too_large`、`unsupported`、`sensitive_path` 记入覆盖缺口。
- 只看范围用 `--preview`；`--fail-on` 只影响门禁，不改变问题清单。
- 自定义规则用 `.ai-code-review/rules.json` 或 `--config`。

### 效率

- 同一文件最多读 2 段，超出先 Grep 定位；每批最多 3 个文件，读完即小结。
- `checklists.md` 只读对应章节，`rule-catalog.md` 按规则 ID 查，不整份通读。
- 不用 `git show`、`git diff --numstat` 重复统计，引擎结果已够。
- 单轮超过约 40 次工具调用就收敛；命令 30 秒无输出立即终止，不重试。
- 超过 20 个文件或 2000 行 diff 时按模块分批，未审部分写覆盖缺口。

## 3. 复核

沿「入口 → 校验 → 业务判断 → 数据变更 → 外部调用」走通成功、失败、重试分支：

| 维度 | 重点 |
| --- | --- |
| 功能 | 输入约束、状态流转、缺失分支、契约、对既有调用方的影响 |
| 事务 | 边界、传播、隔离、`rollbackFor`、同类调用是否绕过代理、外部副作用能否回滚 |
| 异常 | 传播还是吞没、返回值是否掩盖失败、重试上限、幂等与补偿、异常链 |
| 安全 | 鉴权边界、输入清洗、凭据来源、日志是否泄露敏感值 |
| 并发资源 | 共享状态、锁顺序、连接与流关闭、取消与超时、线程池 |
| 性能 | 循环内 IO 或查询、N+1、无界缓存、可测量影响 |
| 设计 | 职责单一、符合项目分层、注释说明原因、有无对应测试 |

Java 重点：`@Transactional` 是否作用于可被代理的 public 方法、是否被同类调用、受检异常是否配置回滚、事务内是否含 RPC、多数据源事务管理器是否覆盖目标。不要仅凭缺少注解就判缺陷。

结论用两个字段：类型（`确认缺陷` / `待验证问题` / `覆盖缺口`）+ 来源（`engine(<rule_id>)` / `contextual` / 两者）。

出报告前自我证伪：

- 模式命中先确认是否已有校验、上游保证或项目既定写法。
- 行号必须来自实际读取，定位不到写「需人工定位」。
- 同一根因合并一条，其他位置进「关联位置」，不按文件重复。
- 资源、并发、链接一致性、兼容性变更、未使用参数，即使证据不足也保留为待验证。

严重度看影响，置信度看证据：低置信不得标严重（保留类除外），风格最高标中，降级要写理由。严重指已证实的数据损坏、资金或权限问题、必然的线上故障；高指较可能造成数据错误、安全问题或主要功能失效；中指有明确边界条件的缺陷或明显维护风险；低/提示指不影响正确性的风格与优化。每个 `reviewed` 文件都要有处置标记（已复核 / 仅静态 / 未复核+原因）。真实凭据只给脱敏位置与类型，不回显，建议轮换。

## 4. 报告

```text
结论：<判断 + 最大风险 + 是否可合并，≤60 字>

评审信息：对象 / 范围 / 层 / 引擎 / 时间 / 覆盖

问题清单（按严重程度排序）

### 【严重】问题标题
- **位置**：`相对路径:行号`（关联：`路径:行号`）
- **描述**：代码事实与触发条件，必要时附证据片段（最多 5 行，脱敏）
- **影响范围**：模块 / 入口 / 数据 / 用户可见性
- **影响**：具体后果
- **复现**：前置条件 → 操作 → 实际 / 预期；静态缺陷写触发条件
- **建议**：改哪个文件、哪个方法、改成什么
- **验证**：最小步骤或命令
- **来源**：engine(<rule_id>) / contextual / 两者｜置信度：高

---

### 【中】问题标题
- **位置**：`相对路径:行号`
- **描述**：代码事实与触发条件
- **影响**：具体后果（可省略）
- **建议**：改哪个文件、哪个方法、改成什么

---

待验证问题
- 问题 / 缺少的证据 / 验证方式

覆盖缺口
- 文件或目录：失败、排除、超限或未评审的原因
```

规则：

- 中文、结论先行；不粘贴引擎英文条目、规则消息或 JSON 片段。
- 问题清单一律用 `### 【级别】标题` + 要点列表，禁止用表格罗列问题；条间用 `---` 分隔，同级别内按影响从大到小排序。
- 严重与高写全部字段；中与低至少写位置、描述、建议，影响可省略；缺位置或建议不合格。
- 位置精确到行，写 `相对路径:行号`；同一根因只列一条，其他位置放「关联」，不按文件重复。
- 影响范围只写受影响模块、入口、数据与用户可见性，不重复描述内容。
- 证据只引代码路径与代码行，出现 `docs/`、`*.md` 或任务文档路径即不合格。
- 事实句式：未校验、未回滚、未加锁、顺序颠倒；禁用「可能」「一般来说」「建议考虑」。
- 引擎的低与提示级命中只给计数，不逐条列出。
- 10 条问题控制在 200 行内；无确认缺陷时直接说明并列出未覆盖范围。

自检：结论可判断 → 字段齐全 → 无编造 → 覆盖缺口完整 → 无表格、无文档路径、无模糊措辞、已脱敏。

## 5. 落盘

用户说「生成评审报告」「输出报告」时，必须写文件，只在对话交付算未完成：

- 交付物：`docs/local/代码评审/review-YYYY-MM-DD_HH-MM-SS.md`，按第 4 节完整写出，重名加序号。
- 引擎证据：`--write-report` 只写 `review-<时间戳>.engine.md`，开头标注「仅作证据」，不能当报告。
- 只写 `.engine.md` 算未完成；写完给路径，只校验存在与大小，不回读。
- 未要求落盘时只在对话交付，不留文件。

引擎不可用（Python/Git 缺失、禁止执行、纯源码评审）：说明原因，不伪造分数与退出码；逐文件记录已审与跳过；在评审信息中标注「仅源码评审，未运行确定性检查」。
