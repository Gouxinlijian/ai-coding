# 后端服务概览

## 目标

扫描当前后端项目，生成一份中文、新人友好且关键结论可追溯的 `docs/服务概览.md`。读者应在十分钟内理解服务定位、模块边界、主要入口、数据流向、外部依赖和运行条件。

## 原则

- 先建立结构地图，再追踪 2～3 条核心流程，不逐文件通读。
- 业务语言优先；代码标识符保留原文，缩写首次出现时解释。
- 每个表名、入口、外调、配置来源和核心流程都附代码或配置来源。
- 不从当前仓库猜调用方。无网关、客户端或部署证据时写“当前仓库无法确认”。
- 不从类名直接断言数据库表名；推断必须标注依据和置信度。
- 不将目录清单、类清单当作文档正文。

## 执行流程

### 1. 读取项目约束和现有文档

读取项目根的 `CLAUDE.md`、`AGENTS.md`、README、构建文件和模块清单。若 `docs/服务概览.md` 已存在，先读取现有文档，保留仍正确的人工说明并更新过期内容，不盲目覆盖。

### 2. 识别语言并加载适配器

| 证据 | 适配器 |
|---|---|
| `pom.xml`、`build.gradle*` 与 Java/Kotlin 源码 | `references/java-spring.md` |
| `go.mod` | `references/go.md` |
| `package.json` 与 Node.js 服务入口 | `references/nodejs.md` |
| `pyproject.toml`、`requirements.txt` 与 Python 服务入口 | `references/python.md` |

只读取命中语言的参考文件。混合语言仓库按可部署服务分别扫描；语言无法确认时列出检测证据并停止，不套用 Java 规则。

### 3. 建立结构地图

按适配器使用 `rg --files` 和 `rg` 收集：

- 启动入口、端口、上下文路径和配置来源；
- 模块及依赖关系；
- HTTP/RPC 路由、消息消费者、定时任务；
- 外部 HTTP/RPC/消息调用；
- ORM、数据源、精确表名及迁移文件；
- 关键框架与能从依赖文件确认的版本。

建立“结论 → 来源文件:行号”证据表。依赖传递得到的版本无法确认时写“版本由依赖管理，当前文件未直接声明”，不编造版本号。

### 4. 追踪核心流程

优先用 `codegraph_explore` 追踪最常用、有状态变化、跨服务的 2～3 条流程。`codegraph_explore` 不可用或结果不完整时，回退到 `rg` 搜索入口标识符，并定向读取入口、业务方法、Repository/Mapper、消息或客户端文件。

每条链路压缩为：入口 → 校验/编排 → 数据读写 → 消息/外调 → 结果。无法确认的中间环节明确写未知，不补齐想象中的调用。

### 5. 按模板更新文档

写入前完整读取 `template.md`。模板是固定信息槽，不是要求虚构内容：没有某类能力时写“不涉及”；证据不足时写“当前仓库无法确认”。关键表格必须填写来源列。

### 6. 生成后校验

- 不保留 `{{...}}`、`...` 等占位内容，也不保留空章节。
- 模块与职责覆盖所有可部署模块。
- 表名分清精确、迁移脚本证据和推断，并标注来源。
- 核心流程的入口、数据层、外调或消息均有来源。
- 调用方无仓库证据时使用“当前仓库无法确认”。
- 已有文档中的有效人工信息未被无理由删除。

## 常见错误

| 错误 | 处理 |
|---|---|
| 只扫主模块 | 从根构建文件展开全部模块 |
| 用 Mapper/Model 名猜表名 | 查 ORM 注解、模型元数据、SQL 和迁移脚本 |
| 看见多数据源依赖就断言多业务库 | 查数据源定义和实际使用分布 |
| 只列 REST，遗漏消息或定时入口 | 三类入口都按适配器扫描 |
| 写“被某系统调用”但无证据 | 改为“当前仓库无法确认” |
| `codegraph_explore` 不可用就停止 | 用 `rg` 和定向读取回退 |
