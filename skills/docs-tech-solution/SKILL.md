# 技术方案文档生成

## 目标

将已确认需求和当前代码事实整理为设计概要类 Markdown 文档，保存到 `docs/{业务名}/YYYY-MM-DD-{主题}.md`。文档应让开发能够按已确认内容实施；未知信息必须显式标记，不得为了“完整”而编造。概要设计只需覆盖架构、模块、数据与核心流程主线，未细化处按对应章节写“未确认”。本 skill 只产出设计概要类文档（架构/接口/数据/配置/迁移层面），不用于需求文档、说明文档、API 文档、报告等其它类型文档，也不用于代码改造方案、重构方案等代码层面的改动规划。

## 输出路径

```text
docs/{业务名}/YYYY-MM-DD-{主题}.md
```

- 从需求中提取稳定、简短的业务名和主题，避免使用“方案”“设计”等无区分度目录名。
- 目录不存在时创建。
- 同日同主题文件已存在时，先读取并判断本次是更新原文还是新主题；确需保留两版时使用 `-2`、`-3` 序号，禁止无提示覆盖。

## 执行流程

### 1. 提取已确认事实

整理业务目标、现状、改动点、约束和明确不变的兼容行为。仅当缺失信息会改变以下任一项时才阻塞并追问：

- 接口契约；
- 数据模型；
- 核心流程；
- 兼容性；
- 上线方式。

其他未知内容继续探索；仓库和需求都无法确认时，在对应节写“未确认”及缺少的证据；系统性、影响实现的待确认项集中记录到第 16 节“待确认事项”表。

### 2. 定向探索代码库

只探索方案范围内的代码和配置：

- 优先用 `codegraph_explore` 定位接口、业务调用链、数据访问、消息和外部客户端。
- `codegraph_explore` 不可用或结果不完整时，用 `rg --files`、`rg -n` 和定向文件读取回退。
- 现有接口、表、字段、配置键、枚举、状态和值域结论必须附 `文件:行号` 证据。
- 对需求中新建且尚不存在的内容标注“方案定义”，不要伪装成代码现状。
- 不在方案范围外做代码审查或顺手提出额外改造。

### 3. 读取规则与模板

写入前完整读取：

1. `rules.md`：叙事、证据、Mermaid、接口六件套、工程决策清单和自检规则；
2. `template.md`：固定 16 节模板。

必须保留模板全部节及原顺序。某节不适用时写“不涉及”或模板要求的等价明确表述，不删除标题，不新增模板未列出的顶层章节。第 10 节工程决策清单子节逐项保留；备选方案与取舍仅在存在多个候选方案时写入 10.1；待确认事项集中写入第 16 节。

### 4. 生成文档

- 结论先行：每节先写设计结果，再写必要说明；只保留影响理解、评审、开发、联调的内容，删除需求复述、重复说明、常识、套话和无依据扩展。
- 简单内容简短表达，不为填充章节扩写；表格、流程图、代码块仅在明显提升理解时使用。
- 关键业务规则、主流程、接口、数据结构、系统影响不得因精简而遗漏。
- 已确认内容使用确定语气，未知内容写证据缺口。
- 每个接口使用地址、请求规格、返回规格、内部查询逻辑、下游推送参数、处理规则六件套；不涉及的套件明确写“不涉及”，不省略。
- 用户未提供人员、工作量或发布日期时，任务排期按阶段和依赖描述，具体时间写“未确认”，不得编造日期、人天或责任人。
- Mermaid、字段表、JSON 示例、SQL/ORM 条件必须相互一致。

### 5. 保存并输出摘要

保存前执行 `rules.md` 的生成后自检，重点过简洁自检：删除任何不影响方案理解和开发实施的句子，确保读者看一遍即可理解核心方案。对话中只汇报文档路径、核心架构、关键决策、未确认事实和不适用章节。

## 失败处理

| 场景 | 处理 |
|---|---|
| 需求仍在方案选择阶段 | 用户明确要“概要设计”时按概要级别生成并标注未确认；仅头脑风暴尚未成文则先澄清，不生成定稿 |
| 关键契约信息缺失 | 只对会改变接口/数据/流程/兼容/上线的缺口追问 |
| 代码证据与需求冲突 | 同时列出现状证据和目标要求，在对应章节说明变化 |
| 代码探索工具不可用 | 回退到 `rg` 和定向读取，记录无法覆盖的范围 |
| 同名文件已存在 | 更新原文或使用序号新建，不静默覆盖 |
| 无法给出排期 | 保留第 14 节，写阶段、依赖和“时间未确认” |
